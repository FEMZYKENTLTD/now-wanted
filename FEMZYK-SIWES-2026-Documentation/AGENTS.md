## 5. CONTENT RULES

### Past-tense rule
The Log Book is a **report book**. All completed activities MUST be written in the
**past tense**.

> GOOD: "I studied the structure of HTML forms and practiced creating a basic user
> registration interface."
>
> BAD: "I study HTML forms." / "I am studying HTML forms."

### Personalization rule
Daily entries describe what the student **personally** did, learned, practiced, observed,
assisted with, developed, tested, corrected or documented. Entries must be personalized
(first person, student-specific) and must vary by day.

### Progressive-learning rule
The Log Book must show a coherent journey from orientation/basics toward a full
database-backed software project — not 28 weeks of repeated generic theory. Planned
arc (used only as a framework, and only where real activity supports it):

> Orientation → Understanding the Organization → Digital Workflows → AI Tools →
> Gig Acquisition / Project Opportunities → Client Requirements → Task Assignment →
> Project Execution → Quality Control → Programming → Web Development → Databases →
> APIs → Software Engineering → System Analysis → System Design → Full-Scale Software
> Development → Testing → Debugging → Documentation → Demonstration → Final SIWES Review.

### No-fabrication rule (highest priority)
Never invent: signatures, stamps, approvals, or supervisor comments — these are
completed by authorized people in the physical world. All SIWES content, dates, attendance,
technologies, activities and evidence for the 2026 submission are verified; do not
introduce unsupported new claims.

### Technology-claim rule
Never claim the student used a technology unless it is confirmed, or clearly framed as a
documented learning activity.

### No-fabricated-evidence rule
Never create a fake screenshot or fake photograph and present it as proof an activity
occurred. Only legitimate evidence may be used (see Evidence section below).

### Anti-repetition rule
Do not fill days with the same activity. Break technical work into realistic components
(environment setup, project structure, requirements, implementation, testing, debugging,
review, documentation) so consecutive days differ meaningfully.

## 14. DAILY ENTRY WRITING STANDARD

Each daily entry answers:
1. What did I do?
2. What did I learn?
3. What tool/technology did I use?
4. What problem/challenge did I encounter, if applicable?
5. How did I improve?

**Confirmed writing-capacity constraint:** each daily input field in the Monday–Saturday
section is **≈ 3 handwritten lines of A4-sized writing space**. Daily entries must
therefore be concise and handwritten-friendly — **approximately 2–3 lines (~15–25 words)
maximum per daily field**. Keep the entry short enough to fit; **no essay-length entries**.
Prefer to transform raw notes into correct past-tense, first-person reporting rather than
fabricate events. (This 3-line estimate is a working constraint; it is NOT permission to
invent page-level headings/boxes that remain unverified.)
